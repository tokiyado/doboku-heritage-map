# 土木遺産アトラス

土木学会の「選奨土木遺産」を地図から探せる、非公式のWebサイトです。
土木学会が運営・監修するものではありません。

- 2000〜2026年度の570件・674地点を収録
- 遺産名・地名での検索、地域・都道府県・選奨年度・種類での絞り込み
- 地図上の数字を押すと拡大し、ピンから各遺産の詳細を表示
- 猿島要塞・三角西港・小樽港北防波堤の3件は、周辺地形を3Dで表示

公開URL：https://tokiyado.github.io/doboku-heritage-map/

## データと写真について

- 遺産の名称・所在地・竣工年・選奨年度は、[土木学会の年度別一覧](https://www.jsce.or.jp/contents/isan/list/index.html)の表記に基づきます。旧地名も含みます。
- 座標は[土木学会の公開マップ](https://dobocolle.jsce.or.jp/digital-map/)（2026年9月27日更新）の掲載位置です。現地測量や実地確認は行っておらず、見学入口を示すものではありません。
- データの取得日は、2000〜2025年度分が2026年9月10日、2026年度分が2026年10月9日です。
- 種類（橋梁、ダム・発電など）は、このサイト独自の分類です。
- **土木学会の写真は掲載していません。** 各遺産の詳細から公式ページへリンクしています。
- 214件の遺産に写真を計375枚載せています。374枚は Wikimedia Commons 由来（CC BY-SA・CC BY・CC0・パブリックドメイン）、1枚は国土交通省ウェブサイトの写真（小樽港北防波堤、公共データ利用規約 PDL1.0）です。写真ごとの作者・利用条件・出典を画面と [THIRD-PARTY-NOTICES.md](THIRD-PARTY-NOTICES.md) に記載しています。
- 複数の施設からなる遺産では、施設ごとの写真を詳細画面で切り替えて表示します。写真の下に施設名を表示します。
- 3Dビューで選んだ自分の写真は、その画面での一時表示だけに使われ、保存も送信もされません。

## ファイル構成

| ファイル | 内容 |
| --- | --- |
| `index.html` | ページ本体 |
| `app.js` | 検索・絞り込み・地図・詳細表示の処理 |
| `style.css` | 見た目の定義 |
| `data.json` | 遺産データ（1行に1件） |
| `coordinate-provenance.json` | 座標の出典と取得日の記録 |
| `leaflet.js` / `leaflet.css` | 地図ライブラリ Leaflet 1.9.4 |
| `photos-mine.js` | ときやどが撮った写真の一覧（`tools/import_my_photos.py` が作る。著作権はときやど・無断転載禁止） |
| `photos.js` | 同梱写真の一覧（作者・ライセンス・出典・施設名） |
| `photos/` | 同梱写真（本体は長辺1280px以内・1枚300KB以下、`-thumb` は一覧用の192px正方形） |
| `sarushima*.jpg` / `misumi-quay*.jpg` | 最初に同梱した写真とその縮小版 |
| `designated.json` | 国の重要文化財（建造物）のうち土木系で、選奨土木遺産ではないもの（`tools/build_designated.py` が作る） |
| `narratives/` | 紹介文の公開用ファイル（`index.json` と遺産ごとの `{遺産ID}.json`）。`tools/build_narratives.py` が作る |
| `narratives-src/` | 紹介文の元データ（内部調査メモを含む）。`.gitignore` で公開対象から外している |
| `tools/` | 紹介文の取り込み（`build_narratives.py`）と、読み込み用の印の更新（`stamp_version.py`） |
| `favicon.svg` | ブラウザのタブに表示するアイコン |
| `.nojekyll` | GitHub Pages にファイルをそのまま配信させるための空ファイル |

件数・地点数・年度の表示は `data.json` から自動で算出されます。データを更新しても、`index.html` の数字を書き換える必要はありません（この README の数字は手で直します）。

背景地図、書体、3D用のライブラリと地形データは外部サービスから読み込みます。オフラインでは動作しません。

## リンクの形式

- `?q=検索語`：検索した状態で開きます（例：`?q=小樽`）。
- `?id=遺産ID`：その遺産の詳細を開いた状態で開きます（例：`?id=2000_4`）。ブラウザの「戻る」で詳細を閉じて地図に戻ります。詳細の「リンクをコピー」でこの形のURLをコピーできます。

## 国の重要文化財（土木系・選奨外）

地図のひし形の印は、選奨土木遺産には入っていない国の重要文化財・国宝（建造物）のうち土木系のものです。サイドバーの「国の重要文化財（土木系・選奨外）も表示」で表示を切り替えられます。

```bash
python tools/build_designated.py
```

- 土木学会の公開マップ（KML）の「国宝・重要文化財（建造物）マップ」の層を読み、1棟ずつの記録を指定の単位（例「旧碓氷峠鉄道施設」）にまとめ、土木系の単位だけを残します。
- 選奨土木遺産と同じ施設の単位は除きます（300m以内に選奨土木遺産の地点がある単位、または手で確かめて同じと判断した単位）。判断の例外は `tools/build_designated.py` の `SAME_AS`・`NOT_SAME`・`NOT_CIVIL` に書きます。
- 照合の結果は `review/designated-report.md`（公開しない）に出ます。

## 紹介文を更新・追加する

紹介文は `data.json` とは別のデータです。元原稿（調査メモつき）は `narratives-src/` に置き、公開用の部分だけを `narratives/` に書き出します。`narratives-src/` と、照合レポートを置く `review/` は Git の追跡対象外なので、GitHub にも公開サイトにも出ません。

いまの元原稿は `narratives-src/heritage-narratives-cumulative570.json`（全570遺産）です。取り込み済みの古いバッチ（試作10件）は `narratives-src/archive/` に移してあり、読み込みません。

1. 新しい原稿ファイルを `narratives-src/` の直下に置きます。累計版で差し替えるときは、古い累計版を `narratives-src/archive/` に移します（直下に同じ遺産IDの別の内容が2つあると、エラーにして止めます）。形式は `{"records": {"遺産ID": {...}}}` か、1件ずつの `{"id": "遺産ID", "public": {...}}` です。
2. 確認だけをするときは、次を実行します。`narratives/` は書き換えず、照合レポートだけを作ります。

   ```bash
   python tools/build_narratives.py --check
   ```

3. 問題がなければ、次を実行します。変わった遺産のファイルだけを書き換え、続けて読み込み用の印（`index.html` の `?v=`）も更新します。同じ原稿で何度実行しても、ファイルは変わりません。

   ```bash
   python tools/build_narratives.py
   ```

4. `review/narratives-report.md`（件数・エラー・注意・公開しなかった注記）と `review/narratives-diff.txt`（今の公開ファイルとの差分）を確認してから、コミットします。

確認の内容:
- **エラー**（1件でもあると何も書き出しません）：`data.json` に無い遺産ID、キーと `id` の違い、名称が `data.json` と違うもの（推測で結び付けません）、同じ遺産IDで内容が違うもの、必須項目の不足・型の違い、出典番号の重複、存在しない出典番号への参照、http(s) 以外の出典URL、1つのファイル内での同じキーの重複。
- **注意**（書き出しは行います）：どこからも参照されていない出典、公開しない項目。

公開する項目と公開しない項目:
- 公開するのは、各件の `public` から許可した項目だけです（見出し・導入文・本文・現地で注目したい点・関係者と役割・出典の番号／資料名／発行主体／URL／該当箇所／発行年／閲覧日）。不要な項目を削る方式ではないので、原稿に新しい項目が増えても自動では公開されません。
- `research_notes`、根拠の区分（`evidence_class`・`evidence_note`）、確認状況（`verification`）、出典の注記（`note`。内部の調査注記が入るため）は公開しません。公開しなかった注記は照合レポートに一覧で出ます。

手元で直した文の保護:
- `narratives/{遺産ID}.json` を手で直した場合、次に原稿から作り直しても上書きせずに残し、原稿との差分を `review/narratives-diff.txt` に出します（ツールが最後に書いたファイルの指紋を `narratives-src/build-state.json` に記録して見分けます）。
- 原稿の内容に戻すときは、遺産IDを指定します：`python tools/build_narratives.py --overwrite 2000_1,2000_3`

画面での読み込み方:
- 最初は `narratives/index.json`（遺産IDと版の一覧、約14KB）だけを読みます。本文は詳細を開いたときに、その遺産の `narratives/{遺産ID}.json`（2〜6KB）を1件だけ読みます。
- 本文のURLには版（中身の指紋）を付けるので、原稿が変わった遺産だけを読み直します。読み込みに失敗しても地図・写真・地点は使え、「もう一度読み込む」で再試行できます。
- 本文などに付いた番号（`source_refs`）は、その遺産の出典番号（`sources[].number`）を指します。番号を押すと、その遺産の出典一覧の該当箇所が開きます。

## 自分で撮った写真を足す

ときやどが撮った写真を、確認してから公開する仕組みです（`tools/import_my_photos.py`）。**著作権はときやど、無断転載禁止**として表示します（MIT License や Wikimedia Commons の写真の条件とは別）。

1. 写真を `OneDrive\土木遺産写真` に入れます（サブフォルダも可。元の写真は動かしも消しもしません）。iPhone の HEIC もそのまま入れられます。
2. 次を実行します。

   ```bash
   python tools/import_my_photos.py
   ```

   - 撮影位置（GPS）から最寄りの遺産の地点までの直線距離で振り分けます。30m以内は自動、100mまでは「確認待ち」、それより遠い写真と位置情報のない写真は未割り当てです。
   - ファイル名に遺産ID（例 `2000_1`）が入っていれば、それを優先します。複数地点の遺産は、どの地点（施設）の写真かも記録します。
   - 同じ写真を2回入れても、1枚として扱います。
3. `mine-src/割り当て.txt` で、確認待ち・未割り当ての写真の遺産を決めます。`写真ID = 2003_4`（複数地点なら `= 2000_7:3`）、候補の `?` を消すと確定、`対象外` で土木遺産の写真として扱いません。
4. `mine-src/確認用一覧.html` をブラウザで開き、写真に人の顔・車のナンバー・個人の家などが写っていないかを見ます。`mine-src/公開判定.txt` に `公開` か `除外` を書きます（`#` から後ろは除外の理由などのメモ）。一覧の「選んだ判定を書き出す」で、判定の行をまとめて書き出せます。
5. もう一度 `python tools/import_my_photos.py` を実行すると、「公開」の写真だけを `photos/mine/` に置き、`photos-mine.js` と読み込み用の印を更新します。「公開」をやめた写真はサイトから外れます。

- 公開する画像は、撮影情報（位置・日時・機種など）を消し、長辺1280px・300KB以下に縮小したものです。一覧用に192pxの正方形も作ります。
- 画面では、自分の写真を Wikimedia Commons などの写真より先に並べ、「写真：ときやど（撮影日 撮影） / 無断転載禁止」と表示します。
- `mine-src/`（元写真の場所・撮影位置・公開前の画像・判定表・確認用一覧）は `.gitignore` で公開対象外です。公開されるのは `photos/mine/` と `photos-mine.js` だけです。

## 公開と更新

リポジトリ：https://github.com/tokiyado/doboku-heritage-map

このフォルダは git で管理していて、GitHub Pages（Branch：`main`、フォルダ：`/(root)`）で公開しています。写真の採否を選ぶための確認用ファイル `photo-candidates.html` は、`.gitignore` で公開対象から外しています。

更新するときは、まず読み込み用の印を最新にしてから送ります。`app.js`・`style.css`・`data.json` などを書き換えたら、必ず実行してください。数分後に公開サイトへ反映されます。

```bash
python tools/stamp_version.py
git add -A
git commit -m "更新内容のメモ"
git push
```

読み込み用の印：`index.html` は `app.js?v=…` のように中身の指紋を付けてファイルを読み込み、`data.json` と紹介文は `<html data-version="…">` の印を付けて読みます。`python tools/stamp_version.py --check` で、印が古くなっていないか確かめられます。

この印で保証できること・できないこと（ファイル名は固定で、サーバーは `?v=` を見ずに今あるファイルを返すため）:
- **保証できる**：新しい `index.html` を読んだ画面は、ブラウザに残った古い `app.js`・`style.css`・`data.json`・紹介文を使わない（URL が変わるため）。
- **保証できない**：GitHub Pages は `index.html` も最大10分ほどブラウザに残すため、反映直後に古い `index.html` が新しい `app.js` などを読むことがある。古い版の中身はサーバーに残らないので、古い組み合わせで動くとは限らない。
- **保証できない**：古い画面を開いたまま更新すると、その画面があとから読む紹介文は新しい版になる。
- そのための備え：`app.js` は `index.html` に必要な部品が無ければ、壊れた画面を出さずに再読み込みを案内する。紹介文は `index.json` と1件ずつのファイルに同じ作成番号（`build`）を入れ、合わないときや消えていたときは、混ぜて表示せずに再読み込みを案内する。古い `app.js` が新しい `index.html` で動く場合は検出できないが、再読み込みで解消する。

GitHub の画面（「Upload files」）から入れる場合は、1回に100ファイルまでなので、`photos` フォルダ（745ファイル）は何回かに分けてアップロードします。

手元で確認する場合、`index.html` をダブルクリックしただけではデータを読み込めません。このフォルダで次のコマンドを実行し、`http://localhost:8000/` を開きます。

```bash
python -m http.server 8000
```

## うまく表示されないとき

- **404になる**：リポジトリの一番上に `index.html` があるか、Pages が `main` / `(root)` を指しているかを確認します。
- **一覧が出ない**：`data.json` が `index.html` と同じ階層にあるか確認します。
- **背景地図や3Dが出ない**：外部サービスとの通信状態を確認します。3Dは WebGL 対応のブラウザが必要です。
- **更新前の画面になる**：ページを再読み込みします。
